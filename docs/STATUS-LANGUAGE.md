# 面向用户的状态语言规范

本规范约束概览、详细报告、PR 评论、交付摘要和技术记录中描述审查状态的中文文案。目标不是罗列内部状态，而是让读者知道：结论覆盖了什么、哪些内容还不知道、下一步该做什么。

所有面向用户的状态说明分为两层：**审查事实**回答“代码中发现了什么”，**下一步建议**回答“用户现在应该怎么办”。事实层包含当前结论、数量与覆盖边界；下一步层给出与页面入口一致的动作。不能因为某个技术状态成立就直接让整页标题承担操作指令，也不能让下一步建议改写或弱化后端已保存的结论。

规范不新增后端顶层状态：后端继续提供 `outcome`、`reason_codes`、`merge_decision` 等事实；前端 [`reviewSituation.ts`](../frontend/src/utils/reviewSituation.ts) 负责把内部状态组合成用户可理解的情景（`title` 为事实、`description` 为边界、`nextStep` 为下一步）；PR 评论由后端 [`publication_renderer.py`](../backend/app/services/publication_renderer.py) 生成，语义必须与情景词表一致。

## 写作原则

1. **先限定范围，再给结论。** 单独成立的“未发现问题”“暂无高优先级问题”必须带“本次检查”“已检查范围内”或等价限定。没有范围限定的否定结论会被读成安全保证。
2. **事实与下一步分层。** 标题和说明描述审查事实与覆盖边界；下一步建议单独成句，并对应页面上真实存在的入口。状态是事实，动作才是用户需要的信息，但动作不能替代事实。
3. **不把部分结果写成完成。** 失败、用户停止、范围缺口、证据缺口、验证失败都不能使用“已完成”“已通过”“未发现问题”等完成态措辞。“部分审查已完成”这类偏正向表达不再使用。
4. **保留未知、未核实和未执行。** 缺失数据、未知状态、未执行验证不得默认为成功、零问题或零成本。无法判断时明确写“未知”“尚未核实”“暂不能给出完整建议”。
5. **区分事实、证据和建议。** 机器确认的问题、候选/未决记录、人工处理、动态验证结果是不同事实；不能用人工标记替代机器复核，也不能用静态审查替代 CI。
6. **结论绑定版本。** 所有结论只适用于记录的审查 Head。确认 PR 更新后提示“PR 已更新，当前审查结果已过期”，以重新审查为主要动作；历史记录仅可在弹窗内显式确认后复制或导出，并保留服务端旧快照说明，不作为当前版本结论。
7. **执行状态与审查结论分离。** 任务/步骤徽章描述执行过程（失败、已取消、运行中）；结论标题描述审查含义和下一步。同一颜色或词语不跨轴复用，参见 [`StatusBadge.vue`](../frontend/src/components/common/StatusBadge.vue) 的三条语义轴。
8. **完成不等于安全。** 使用“执行已完成”或“审查执行已结束”描述任务或步骤；绿色执行状态只表示该执行单元完成，不能作为 PR 安全或合并批准。整轮结束通知使用信息色，具体风险读取结论。
9. **验证通过必须限定范围。** `reportValidationLabel("passed")` 使用“当前 Head 的受控检查通过”；辅助说明必须指出仅覆盖已记录检查，不代表整个项目 CI 全部通过。验证账本入口可核对来源、阶段、快照绑定与原因。
10. **合并建议是审查策略输出。** `fix_blockers` 等状态来自 RepoGuardian 对已确认问题严重度的划分，不是 GitHub Mergeability 或分支保护规则。对外使用“建议合并前处理的高优先级问题”而非“阻断问题”；确需保留“阻断”时，必须同时说明它不代表 GitHub 会阻止合并。

## 情景词表

| 情景键 | 审查事实（主标题） | 语气 | 下一步建议 | 主要动作 | 复制语义 | 适用条件 |
| --- | --- | --- | --- | --- | --- | --- |
| `clean` | 本次检查未发现需在合并前处理的问题 | success | 预览并复制 PR 评论，结合项目验证和人工审批决定是否合并 | 复制 PR 评论 | 预览后复制 PR 评论 | 无已确认问题，范围完整，无阻断性限制；仅计量记录未知时须附注说明 |
| `nonblocking` | 发现 X 项改进建议，暂无高优先级问题 | info | 查看建议并评估影响，或复制 PR 评论与作者讨论 | 查看建议 / 复制评论 | 复制 PR 评论 | 只有 Medium/Low 等非高优先级建议 |
| `blockers` | 发现 X 项高优先级问题，建议修复后复审 | danger | 查看高优先级问题的证据并修复，再基于新提交重新审查 | 查看高优先级问题 | 复制审查意见 | 数量来自后端高优先级键；缺失时不补造 X |
| `evidence_gaps` | X 项疑点需要进一步确认 / 历史问题经代码核验仍存在 | warning | 查看未确认事项并补齐代码或目标依据 | 查看未确认事项 | 复制审查记录 | 只计算未决候选；调查、作者声明和交付准入限制分别描述 |
| `scope_incomplete` | 还有 X 项约定检查未完成 | warning | 查看未检查范围，核对原因后决定补查或重审 | 查看未检查范围 | 复制审查记录 | X 为明确的未完成目标数；计数与完整性标记冲突时提示核对 |
| `runtime_limits` | 审查已结束，但结果可靠性仍需核对 | warning | 查看运行限制，核对执行与验证记录 | 查看运行限制 | 复制审查记录 | 执行或验证记录不足以支持结论；单纯计量未知不改变已检查范围的首要事实 |
| `validation_failed` | 本次记录的动态检查未通过 | danger | 查看失败记录，核对检查范围、来源与失败原因 | 查看失败记录 | 复制审查记录 | 与当前 Head 绑定的受控检查失败，不泛化为全部 CI 失败 |
| `failed` | 审查中断，尚无完整结论 | danger | 查看错误并处理运行故障，然后重新审查 | 查看错误 / 重审 | 复制部分审查记录 | 执行失败，未形成完整结论 |
| `cancelled` | 审查已停止，已保留部分结果 | warning | 查看已保留结果，确认未完成范围后决定是否重审 | 查看已保留结果 | 复制部分审查记录 | 用户主动停止任务 |
| `stale` | PR 已更新，当前审查结果已过期 | warning | 重新审查此 PR，基于最新提交生成新结论 | 重新审查 | 次要入口：确认后复制带说明的历史记录 | 检查发现远端 Head 已变化 |
| 远端检查未知 | 暂时无法确认 PR 是否有新提交 | warning | 重试检查 | 重试检查 | 显式确认后复制带未知说明的历史记录 | 不将未知原因直接认定为 GitHub 断网 |
| 摘要获取失败 | 当前无法读取完整审查结论 | warning | 重试加载摘要 | 重试加载摘要 | 不提供复制 | 后端摘要加载失败，不能反推审查失败 |

### 情景描述要求

- `clean`：必须说明“本次检查”或“已检查范围内”，并补充未覆盖路径、动态验证和人工判断的边界。
- `nonblocking`：说明建议数量，并明确是否在合并前处理取决于项目要求和实际影响。
- `blockers`：说明高优先级问题数量，并给出“修复后在新提交上重新审查”的动作；说明该建议不是 GitHub Mergeability 或分支保护结论。
- `evidence_gaps`：说明仍有候选、关联调查或发布证据需要补充代码或目标依据；只有运行或计量异常时不得使用该标题，也不得暗示已确认代码缺陷。历史复核已用当前代码确认既有问题时，必须与“本轮 Diff 未新增问题”分开表述，不得写成“目前没有可确认的问题”或“未决事项不等于已确认缺陷”；已核验风险应进入正式风险章节，而不是“仍需确认的事项”。
- `scope_incomplete`：给出已完成/总数；没有目标记录时写“检查范围尚不明确”，不要写“部分检查尚未完成”。
- `runtime_limits`：分别说明约定目标检查情况与执行或验证记录完整性；仅计量未知且静态检查完整时首要事实仍是“已检查范围内未发现已确认问题”，计量不完整另行披露，未知用量不能作为完整统计。没有明确原因的旧记录使用“审查结论暂不完整”，保留未知，不虚构候选或代码缺陷。关联调查未完成不能反推初始静态目标未检查。
- `validation_failed`：说明验证与当前版本绑定，静态结论不能替代修复后的验证；只描述“本次记录的动态检查”，不写成“当前版本存在验证失败”这类泛化结论。
- `failed`：说明执行错误中断，已保留中断前记录；不要写“审查未完成”这种无法区分原因的表达。
- `cancelled`：说明由用户停止，剩余范围未完成；不要写“审查已取消”后继续使用完成态措辞。
- `stale`：说明 PR 已有新提交，结论只适用于审查时的 Head；主要动作是重新审查。概览和报告共用历史交付确认组件，次要选项明确为复制或导出带旧快照说明的历史记录。确认控件必须位于当前模态框内，切换情景不得卸载待确认控件；复制成功不代表 Head 恢复一致。失败或取消任务仍须保留部分审查记录语义。

### “已确认”的边界

“已确认”“机器已确认”“已核验”“受控检查通过”“执行已完成”描述的是不同事实，不得互相替代：

| 说法 | 只说明 | 不说明 |
| --- | --- | --- |
| 执行已完成 / 执行已结束 · 有限制 | 任务或步骤已结束，以及是否存在运行限制 | PR 安全、问题为零、可以合并 |
| 代码证据已确认 | 该问题已有绑定的代码证据支持 | 审查通过、项目 CI 通过、可以合并 |
| 已核验（历史讨论/依赖） | 对应历史主张或依赖已用固定代码核对 | 整轮审查完整或风险已消除 |
| 当前 Head 的受控检查通过 | 该记录覆盖的检查通过 | 整个项目 CI 全部通过 |
| 本次记录的动态检查未通过 | 该记录覆盖的检查未通过 | 全部 CI 失败或静态结论无效 |

执行状态使用“已结束 · 有限制”，并在历史记录和概览中给出具体限制类型，例如“2 项检查未完成”“模型用量记录不完整”；不得只显示笼统的“存在警告”。

### 数量与入口

- 候选问题与关联调查可能重叠，不相加为“问题数”。只有调查未决时写“X 项关联调查尚未完成”，使用“查看未完成调查”展开覆盖页调查记录。作者声明范围未知、未通过交付准入的记录分别说明，不冒充未决代码问题。
- `scope_incomplete` 的目标计数明确且小于总数时才计算剩余数量；没有目标记录显示“检查范围尚不明确”，计数相等但标记不完整显示“检查范围完整性尚待核对”，不显示“还有 0 项未完成”。
- “查看高优先级问题”“查看建议”“查看未确认事项”分别带入后端高优先级键、建议键和未决状态筛选；“查看未检查范围”筛选非 examined 目标。
- 概览的高优先级问题与改进建议按来源拆分展示（“本轮 Diff N 项”“历史复核 N 项”），每个来源数量进入问题页时带入相同的键筛选与来源筛选。历史复核已核验风险作为同一列表中的条目展示，并标注“不计入本轮 Diff 新增”；与本轮记录指向同一缺陷、已按独立计数合并的历史讨论不再重复列出。来源数量之和与总数不一致（例如旧冻结计划缺少去重标注）时不展示拆分，只显示总数。
- 问题页的数量必须与条目一一对应：后端提供键列表（含空列表）时严格按键筛选，只有旧记录完全没有键字段时才回退到展示严重度。历史风险已进入问题工作台，因此存在历史高优先级风险时主操作仍是“查看高优先级问题”，不再降级为“查看完整报告”。
- 历史风险已获代码核验但尚未分级时，可能没有高优先级或建议键；`historical_discussion_unresolved` 场景主操作与下一步均引导到完整报告，不把已核验风险带到空问题列表，也不把它降为未核实疑点。
- “查看运行限制”“查看错误”“查看失败记录”进入技术记录中的对应区；未知 Head 的“重试检查”重新发起有身份校验的检查并保留原复制或导出动作，取消或切换来源使旧动作失效。

## 合并建议标签

PR 评论、交付摘要和详细报告使用后端 `merge_decision.label`。可操作状态保持三种：

| 状态 | 标签 | 含义 |
| --- | --- | --- |
| `conditional_merge` | 本次检查未发现需在合并前处理的问题 | 没有高优先级项，也没有已确认的非高优先级建议；仍需结合 CI、审批和人工判断 |
| `conditional_merge`（含非高优先级建议） | 发现 X 项改进建议，暂无高优先级问题 | 没有高优先级项，但有已确认的 Medium/Low 建议 |
| `fix_blockers` | 发现 X 项高优先级问题，建议修复后复审 | 存在已核验的 Critical/High 问题 |
| `resolve_unknowns` | 按原因显示范围、证据或可靠性限制 | 存在影响决策的检查缺口或记录限制；仅计量未知和作者声明截断不单独进入该状态 |
| `unavailable` | 暂不能给出合并建议 | 失败、用户停止或缺少有效审查事实 |

评论首行在失败/停止时明确写“审查中断，尚无完整结论（部分审查记录）”或“审查已停止，已保留部分结果（部分审查记录）”。

`resolve_unknowns` 保持同一系统状态，标签按上述原因和计数细化；当前 Head 已有明确受控检查失败时直接说明动态检查未通过。混合原因不删除任何限制明细，未知原因不得默认归为代码证据不足。概览和后端新生成报告使用相同的计数边界；旧冻结计划保留原正文。

## PR 评论章节结构

所有状态共用同一套章节含义，只按风险调整顺序；没有内容的章节不输出，避免出现只有标题或只有行动文案的空章节：

| 章节 | 含义 | 何时出现 |
| --- | --- | --- |
| 结论（首行，无标题） | 合并建议与符号 | 始终 |
| 需要处理的问题 | Critical/High 等需在合并前处理的问题 | 有可交付的高优先级问题时 |
| 已核验的既有风险（`## 已核验的既有风险`） | 历史复核已用当前代码确认仍存在、但不属于本轮 Diff 新增的问题 | 有已核验的历史风险时 |
| 本次变更理解（`## 变更理解`） | 作者目标与绑定证据的代码观察 | 正常完成时 |
| 其他建议（`## 其他建议`） | Medium/Low 等非阻断建议 | 有可交付的非高优先级建议时 |
| 仍需确认的事项（`## 仍需确认的事项`） | 影响合并判断的限制、缺口、尚未完成的历史调查、省略说明 | 有实际未确认条目时 |
| 审查范围与补充信息（`## 审查范围与补充信息`） | 完整版的审查范围、来源与验证明细 | 没有未确认条目、仅完整版有明细时 |
| 下一步（`## 下一步`） | 面向作者的单段行动建议 | 始终 |
| 快照与验证边界 | Commit、只读范围、CI 与审批边界 | 始终（文末） |

- 有可交付的高优先级问题：结论 → 需要处理的问题 → 已核验的既有风险（如有）→ 变更理解 → 其他建议（如有）→ 仍需确认的事项（如有）→ 下一步。
- 只有可交付的非高优先级建议：结论 → 已核验的既有风险（如有）→ 变更理解 → 其他建议 → 仍需确认的事项（如有）→ 下一步。
- 无已确认问题但审查不完整：结论 → 已核验的既有风险（如有）→ 仍需确认的事项 → 下一步；不追加变更理解。
- 无问题且检查完整：结论 → 变更理解 → 仍需确认的事项（如有）→ 下一步。
- 执行失败或主动停止：结论与部分记录声明 → 变更理解 → 已核验的既有风险（如有）→ 仍需确认的事项 → 下一步（重新审查）；不将原始机器确认记录升级为可交付缺陷。

历史复核结果必须按证据状态分流：取得独立代码证据且判定仍存在的记录进入“已核验的既有风险”，并使用与当前问题相同的等级标记与建议格式；只有“仍存在”标签而没有可引用证据、或尚未完成核验的记录进入“仍需确认的事项”。两类都标注“不计入本轮 Diff 新增问题”，不能把已核验风险写成“待核实”。

详细评论与简洁评论采用相同的主章节顺序与相同的风险判断；完整范围、来源和验证明细以三级标题展开。只有确实存在未确认条目时才使用“仍需确认的事项”；完整版仅有范围与来源明细时使用“审查范围与补充信息”，简洁版不因完整版明细而多出章节。快照与 CI、审批边界统一保留在文末。前端预览把历史标题映射到同一组章节（如“建议项”映射为“其他建议”），不改变旧记录的原始 Markdown。

### 计数口径

- **独立缺陷数**面向 PR 作者：同一缺陷同时出现在本轮审查与历史复核时只计一次。去重只依据执行器保存的严格关联（主体、触发条件、影响三项均为 true 且无新信息），文件路径相同或标题相似不构成同一缺陷。
- **证据来源数**面向技术审计：分别记录本轮记录与历史复核的高优先级、建议数量，不合并展示。
- 标题与概览指标使用独立缺陷数；技术审计同时给出两者。旧冻结计划缺少独立去重数量但保留合并标注时，展示层按标注合并；完全没有去重标注时才回退为来源相加，不推测未保存的关联。
- 概览的来源拆分必须可对账：只有“本轮 + 历史 − 已合并”等于总数时才展示拆分，否则只给总数，避免出现无法在问题页找到的构成。

## 禁止与替换

| 避免 | 改为 | 原因 |
| --- | --- | --- |
| 本次静态审查未发现需处理的问题 | 本次检查未发现需在合并前处理的问题 | 否定结论需要范围限定，并说明“合并前”这一口径 |
| 部分审查已完成 | 部分检查尚未完成 | 避免把缺口读成进展 |
| 审查未完成 | 审查中断，尚无完整结论 / 审查已停止，已保留部分结果 | 区分失败与用户主动停止 |
| 审查已停止 | 审查已停止，已保留部分结果 | 保留结果语义，避免被读成完整审查 |
| 已有验证未通过 | 本次记录的动态检查未通过 | 绑定版本与记录范围，说明是记录而非泛化结论 |
| 审查结果基于旧代码版本 | PR 已更新，当前审查结果已过期 | 先给事实，再给影响 |
| 未发现阻断性问题（单独出现） | 本次检查未发现需在合并前处理的问题 / 发现 X 项改进建议，暂无高优先级问题 | 单独出现时容易被读成安全保证 |
| 阻断问题 / 阻断性问题 | 高优先级问题 / 建议合并前处理的问题 | “阻断”容易被读成 GitHub 会阻止合并 |
| 审查已通过 / 代码安全 | 本次检查未发现需在合并前处理的问题 | 静态审查不提供通过或安全保证 |
| 存在警告 | 已结束 · 有限制，并列出具体限制类型 | 警告可能来自计量异常，不能暗示代码风险 |
| 已确认问题（不带范围） | 代码证据已确认的问题 | 说明确认的是代码证据，不是审查通过 |
| 目前没有可确认的问题（历史复核已确认既有缺陷时） | 本轮变更范围内未新增代码证据已确认的问题；历史复核确认的既有风险仍存在 | 当前 Diff 与历史复核是不同事实域 |
| 当前版本存在验证失败记录 | 本次记录的动态检查未通过 | 限定为已记录的受控检查，不泛化为全部 CI |
| 部分审查记录（正常完成时） | 复制 PR 评论 / 复制审查意见 | 只有失败或停止才使用“部分审查记录” |

## 参考实践

- GitHub Copilot code review 在摘要中先说明审查了哪些变更，再列问题，避免把“未发现问题”写成整体安全结论。
- CodeRabbit 区分 actionable comments 与 nitpicks，并在 walkthrough 中说明审查范围。
- SonarQube Quality Gate 区分 passed、failed 与 not computed；缺少分析时不会显示为通过。
- Google Engineering Practices 要求 review 评论可执行，并区分阻断项与建议项。

这些实践的共同点是：结论要说明覆盖范围，区分高优先级与非高优先级，并给出可执行的下一步。本规范采用相同结构，但不复制任何外部产品的具体文案。

## 维护

- 新增或修改情景：同步更新 [`reviewSituation.ts`](../frontend/src/utils/reviewSituation.ts)、[`review-situation.test.mjs`](../frontend/tests/review-situation.test.mjs) 和本文件；涉及 PR 评论时同步 [`publication_renderer.py`](../backend/app/services/publication_renderer.py) 与后端渲染测试。
- 修改后端标签或评论结构：重新生成 `frontend/tests/fixtures/publication-plans.json` 与 `review-comment-options.json`，并运行 `backend/tests/test_api_contract.py`。
- 文档变更后核对 README 与本地 `docs/review-output.md`、`.trellis/spec/frontend/` 中的链接与词表是否一致。
- 不在组件内另写结论措辞；概览与报告统一读取 `reviewSituation.ts`。

## 页面用语与统计口径

- “机器已确认，发布准入未通过”对用户表述为“代码问题已确认，但暂不能生成可发布评论”；发布资格与人工处理仍独立记录。
- 核心入口使用“技术审计记录”“发布或复制到 GitHub”“PR 代码版本”；Head/SHA 等精确信息在快照和技术记录保留。
- 范围说明使用“已检查 X/Y 项约定范围，N 项待补查”；缺失仍为未知，范围不一致时使用“尚无法确认检查范围是否完整”。
- 动态验证通过须限定为“当前 PR 版本已记录的对应检查通过”，不能推断 CI 全通过。
- 讨论数按保存线程、评论数按保存 ID 去重；引用数属于被审查引用的部分。复核完成计数包含背景说明，不等同所有讨论都有代码验证。
