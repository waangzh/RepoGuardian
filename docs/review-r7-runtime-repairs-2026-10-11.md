# r7 运行问题修复记录

本阶段针对 r7 接入验收暴露的重复审查、问题更新契约、重复独立验证和解析失败后用量丢失进行局部修复。没有修改历史验收产物，没有调用真实模型，也没有改变每样本 200 次调用 / 100 万 tokens 的整轮预算。

## 修复行为

### 审查随证据进展收敛

原生 `review_step` 按当前 diff、只读正文、已展示的文件发现事实和 base/head 生成证据指纹。同一证据最多审查两次；已有诊断后，连续两轮取证无进展也结束当前审查。新正文或新文件发现事实仍允许继续，重复路径库存不算新进展。

停止保留候选和已验证记录，最新 attempt 标为 `unknown / review_step_no_evidence_progress`，terminal 为 `no_new_context`。覆盖门不能重启这类停止，也不能把保留的旧有效记录计为完整完成。最近三条有界工具反馈和请求进入原生输入，`file_read_diff` 明确提供真实文件和 hunk 白名单；预检和发送使用一致范围。

### 已闭合问题的精确重复更新

仅在完整输入快照一致、历史证据仍可信且问题账本状态一致时，从已验证记录生成有界闭合目录（最多八条、1,500 字符）。模型可逐字段重复该目录中的更新；服务端将其作为幂等 no-op，不重复应用到问题状态或覆盖账本。

不同 reason、证据、状态、replacement、快照，未知旧 ID，以及用已闭合 ID 表示另一个问题，仍拒绝整份记录。活跃问题的身份和更新规则保持严格。没有闭合目录时沿用原记忆预算，避免额外目录使后续 workset 准入失败。

### 批内精确复用成功的独立验证

一次 `verify_issues()` 内，完全相同的验证输入可复用已经通过 schema 和决策校验的 keep/drop 结果。指纹覆盖缺陷主张、主/支撑证据、只读正文、完整性、规则、模型、base/head 和 Unit 范围，排除候选身份与动态剩余次数。

复用为每个候选重新绑定 issue ID，并记录 `verifier_reuse` 审计，不创建 alias，也不重复累计调用或 usage。失败、unresolved、不完整证据、取消、预算延迟和未知 usage 不进入成功缓存；跨批次不复用。相同主锚点但主张或上下文不同仍需分别验证，因此不能推断 Checkmate 的 53 次调用会降到 25 次。

### 解析错误仍保留实测 usage

JSON fallback 解析错误统一包装为 `LLMProviderError`，使既有 adapter 的异常路径附带已经返回的 usage；错误消息只包含行列位置，不回显原始响应。原生审查先经过候选解析路径，保留 schema 拒绝审计。

已返回用量的解析失败不再从高层观察记录中丢失。取消请求没有 usage 时仍保持未知，不补零，也不能据此计算完整成本。

## 验证与限制

新增回归覆盖同证据重复报告、拒绝读取、新正文、新/重复文件发现事实、覆盖门不重启、闭合更新幂等及负例、活跃问题保留、成功验证复用及独立身份、失败/未知用量不复用、指纹边界，以及五类 adapter 坏 JSON 后的 usage 传播。

本地完整后端回归通过：1,037 passed、2 skipped。随后新增边界用例、覆盖门及等价文件发现查询修正的相关回归通过：76 passed；Ruff 全库与差异空白检查通过。交付提交还会在独立 Git 快照中验证，具体结果以交付说明为准。

这些结果验证本地控制流与契约，不证明真实模型的覆盖、效率或审查质量已经改善。问题 identity 改写、其他非法 `next_need`、真正缺失的契约证据和不精确重复的候选仍可能导致 partial / invalid。下一轮真实验收需要继续冻结样本、SHA、diff、模型与预算，并使用新目录执行“先 1 个、核验后再 4 个”；本阶段未启动该验收。
