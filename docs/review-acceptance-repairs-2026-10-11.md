# r5 接入问题的产品修复（2026-10-11）

本次修复基于冻结的 r5 问题与当前代码回归，不改写历史结果，不调用真实模型、不执行被审查仓库代码。修复后的五样本完成率、召回率和语义准确率仍需新实验验证。

## 运行与账务

- AACR `run_sample()` 创建独立的 `ReviewRunBudget`，使用与生产服务相同的配置并激活整个审查图；不同样本不共享消费。
- 结果新增 `run_budget`，保留逐 attempt 的估算、实际用量、释放、超额及未知预留；usage 缺失不释放或填零。
- `effective_model_profile` 单独记录 Provider 最终选择的来源和窗口，避免将通用配置快照误认为实际请求窗口。
- 协调目录、补查和验证只在预算变化或未来保留解除后重新准入。已发送的失败或未知调用仍由缓存阻止重发；延期验证只重新验证延期候选，不重复执行 Policy、生成候选或累加已有 usage。

## 身份与完成

- 服务端绑定 Unit 时同步投影来源，子工作集聚合到父 Unit 后不遗留 `unassigned`，保留其他真实 Unit 的来源。
- 缺失、无效或失败的审查记录不能计入完整覆盖；执行完成与可信审查完成仍是两个字段。
- 去重审计记录明确的 canonical Unit。跨 Unit 两跳 alias 可继承最终状态；歧义、环和没有明确映射的同名身份不能借用其他 Unit 的成功状态。
- 补查仍作为独立记录保存。原 Unit 的覆盖缺口不因一个补查候选被确认而自动消失；重新检查原目标须保留当前快照、证据及覆盖账本。

## Python 分支证据

Python 条件体内的证据新增 `branch_claim`，例如：

```json
{"file_path":"app.py","existing_code":"        mask = float(\"-inf\")","branch_claim":{"condition_code":"directml","arm":"else"}}
```

`condition_code` 必须对应实际 Python 条件表达式；`arm` 为 `if`、`else` 或 `both`。`both` 只用于引用覆盖整个条件结构。位置仍由服务端解析，不接收模型计算的 resolved 行号。

服务端静态解析对应 Head/Base 文件并核对 AST 范围。缺少必要声明、分支不一致或声明无法核验时保留 unresolved。Verifier 的分支反证也必须在同一段已显示正文中唯一定位并满足范围，不跨片段拼接。此防线验证位置与分支归属，不证明一般语义正确性，不执行目标代码；其他语言的分支声明暂不受支持，明确声明后无法核验会保留未知。

## 验证与后续实验

后端使用 `uv run pytest -q -p no:cacheprovider` 和 `uv run ruff check .`；前端使用 `npm test`、`npm run build`。定向回归覆盖额度释放、未发送拒绝、调用身份恢复、两跳 alias、缺失记录、来源传播以及 `else` 的 `-inf` 误归因。真实 SDK 的 HTTP 参数通过本地 MockTransport 核对，不等于供应商已接受或执行该参数。

本次工作区全量后端回归为 991 项通过、2 项跳过；随后追加真实 SDK、节点级身份及嵌套分支回归，最后定向验证 72 项通过、Ruff 通过。前端 19 项测试与构建通过。第二阶段提交的独立 Git 快照中，46 项核心回归与 Ruff 通过。跳过项不作为已验证分支，工作区尚有其他未提交材料，交付只包含相关实现及其必要回归。

后续真实 AACR 验收使用新目录，继续核对冻结 SHA/diff、实际配置和实现指纹，并分别报告完成率、覆盖、confirmed、未确认结果、真实请求和未知用量。Python 参考读取禁区仍不是 OS 级沙箱；历史 r5 产物与成绩保持原样。
