# r6 接入缺陷的修复与验证

依据 r6 报告和本轮产物继续修复生产契约。历史 r6 数据保持原样，本次不调用真实模型、不执行被审查仓库代码，也不提高预算。r5 与 r6 的预算范围不同，不能据覆盖增加推断同预算效率提升。

## 根因与变化

- `review_step` 先解析 Issue，再解析可选 `next_need`。后者 schema 错误曾抛出整次异常，已接受候选没有进入生成与过滤。现在拒绝非法动作、保留有效候选和检查记录，并将最新 attempt 标为 invalid，阻止完整判定和复用。动作提示从服务端注册表生成，不把 `type/file_path/symbol` 解释为合法动作。
- `condition_code` 兼容单个 `if/elif` 条件头，随后仍核对实际 AST 条件、side 和分支范围；格式兼容不会把错误分支变成有效证据。
- 完成门曾把未决问题和未验证依赖合并到 `omitted_targets`。现在 `target_coverage` 表达检查覆盖，`contract_coverage`、`unresolved_questions`、`unresolved_dependencies` 单独表达契约缺口。契约未闭合仍阻止整体完成；真正未检查、失败或无效记录不能借此获得完整状态。父子聚合保留有效检查记录，不以未决依赖抹掉已经执行的检查。
- schema 候选没有观察到真实目标生命周期时，final 明确为 `not_published/canonical_lifecycle_not_observed`。schema 和补查改名的原身份均继承真实目标终态；多跳、跨 Unit、环和歧义保留原有边界，合成 `audit_gap` 不能作为成功终态来源。
- Verifier 原输入同时重复携带 `lines` 和 `added_lines/removed_lines`。有完整双侧 `lines` 时去掉副本；旧式只有新增/删除行的输入保留兼容。超过 60,000 字符时只选择完整 hunk，并标记 evidence_complete=false，不在 JSON 或代码中间切断。
- ComfyUI 两条已确认候选具有同一文件、符号、hunk、side 和相邻坐标，因根因描述措辞不同未进入语义去重组。现在相邻候选进入有界的语义判定；模型拒绝合并、异常或超时均保留候选，不因位置相近自动合并。精确补查请求的已有缓存与去重规则保持不变。

## 验证边界

离线回归覆盖完整 Unit 流程中的非法动作拒绝、候选保留、分支格式兼容、终态继承、分类后的覆盖门、双侧反证、超长输入及语义去重的合并/保留分支。测试使用项目自建 fixture 仓库与本地模型桩；这不构成目标仓库动态验证。

只读重放五份 r6 历史审计事件后，原先 37 条 `reidentified` 均得到明确处置，Gemini 的 2 条、RAGFlow 的 1 条缺失目标生命周期被明确保留为未发布。重放只验证审计表达，不改写历史产物、候选语义或验收成绩。

代码检查使用后端 `uv run pytest -q -p no:cacheprovider`、`uv run ruff check .`，前端 `npm test`、`npm run build`。交付时另验证已提交 Git 快照，检查测试不依赖本机 `.env` 或未提交辅助文件；实际结果在本次交付说明记录。

最终工作区全量后端回归为 1,014 项通过、2 项跳过，Ruff 通过；前端 21 项测试和构建通过。独立复核的 18 项新增回归通过。跳过项不作为已验证分支。

仍需新一轮冻结真实验收测量完整覆盖、请求数、实测用量和候选语义质量。减少重复正文不等于已证明总 tokens 下降；增加语义去重可能产生额外调用。Python 读取禁区仍不是 OS 级沙箱，供应商 thinking 执行语义仍未独立验证。
